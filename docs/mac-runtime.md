# macOS runtime, isolation and durability

## Startup and production composition

No arguments selects production. Only explicit `--preview` or `--mock-smoke` enters `PreviewEnvironment` before framework/services/storage/transport initialization. Unknown/conflicting modes and production scenarios are rejected. A mock-only environment prevents production platform operations rather than silently changing the selected mode.

Production startup reads the private saved draft and actual app/network catalogs. It does not start TUN or request administrator authorization. `ProductionClientBackend` composes real native catalogs/icons, bound HTTPS/DNS resources, private caches/drafts/generations, authenticated helper IPC and `MacXrayCoreRuntime`. Views only call the injected backend. The preview uses a separate fixture implementation and temporary directory; production never receives synthetic nodes, paths, latency or traffic charts.

Clicking Connect validates the saved policy and local pinned core, probes only required automatic groups, authorizes the helper, and starts a transient TUN + loopback resource SOCKS generation before any missing-rule download. The temporary configuration admits only the resource inbound and its explicitly bound upstream DNS; ordinary TUN traffic is blocked until the complete policy/assets pass validation. The original document and fixed inventories are retained. The temporary generation is never published to the saved-generation store. Failure/cancellation restores the prior runtime without publishing partial rules; successful preparation applies the complete policy through the normal durable transaction. An unchanged running resource route is reused without restarting TUN.

## Configuration transaction

The coordinator snapshots policy/assets and validates every external DAT reference against actual protobuf kind/tag before changing the core. Runtime fingerprint is JSON plus sorted asset hashes; generation identity also includes saved DSL. Metadata-only publication does not restart. A disk generation is not assumed to be an actually running core.

Apply failure/cancellation independently attempts core recovery and saved-pointer recovery, even if one fails. Recovery is not canceled by the caller. Failed recovery reports unavailable. Fixed executable inventories remain in the desired policy through retry. Every lifecycle change has a concrete cause; logging failure cannot change its verdict.

`AtomicGenerationStore` publishes immutable verified generations with file/directory fsync and atomic pointer replacement. Drafts preserve incomplete onboarding choices in a checksummed, bounded current/previous store. Sensitive files are created 0600, private directories 0700. Neither store assumes an attacker-controlled shared directory.

## Resource bootstrap and bound runtime probes

Rule resources use `XrayResourceTransport`, which delegates to the existing shared `DefaultProxyDownloadTransport`. Every request captures an explicit `ResourceExitSnapshot.Xray(port)` and owns its client/cancellation. No system proxy resolver or direct HTTP fallback is used for rules. Subscriptions have a separate mandatory direct transport. SOCKS passes destination names to Xray, and the resource routing rule precedes DNS/local/China/application rules so every rule download uses the fresh successful non-DIRECT node chain from the default group, bound to the non-home interface. HTTPS redirects, certificates and bounded streaming remain enforced. Background rule-catalog requests capture the saved port; pending profile rule preparation captures its candidate port. An unavailable captured port fails without inheriting a replacement route.

The app carries the exact official `Xray-macos-arm64-v8a.zip` under `Contents/MacOS/core/`. Startup first checks the pinned executable cache, otherwise verifies the bundled archive and independent executable SHA-256 before durable local extraction. Missing/corrupt bundle payload is a fixed actionable startup failure; startup never downloads its own bootstrap core. Packaging verifies both hashes, preserves the Xray license and records provenance in `Contents/Resources/CORE.json`. CI acquires this build-time input explicitly; `Package-Mac.py --xray-archive` itself is offline. Rider builds copy the `artifacts/core` payload and prepare the same complete NativeAOT app/helper bundle automatically.

`DirectSubscriptionResources` is independent of core/helper readiness. It captures the chosen non-home interface and DNS upstream, uses `BoundHttpsResourceTransport` with `UseProxy=false`, and binds both HTTPS and DNS sockets before connecting. This prevents an already-running TUN from redirecting a subscription through the global proxy. Providers and HTTPS redirects retain the same snapshot. Direct failures never invoke an alternate proxy or interface; diagnostics preserve stage and timeout/cancellation distinction while redacting endpoint credentials. Explicit updates preserve existing validated caches on failure. No local YAML is required; the foldout is optional.

The managed Rider entrypoint handles explicit preview/mock arguments and safety checks first. Only managed macOS production replaces itself with the generated NativeAOT executable via `execv`, retaining the main PID/lifetime. This preserves the existing helper's signed native GUI authentication without trusting a mutable managed DLL host. `RiderProduction.targets` and `Build-MacProduction.py` prepare the app incrementally after normal builds, verifying source/payload hashes and signatures on reuse. Inner AOT publishes disable the outer target to prevent recursion. Package creation performs only mock-smoke execution; the production handoff is not invoked during tests.

Startup validates caches before network requests; explicit subscription update forces refresh. Providers use the same snapshot. Official Meta indexes are tied to a commit and raw YAML blob hashes before DAT compilation. The core archive, checksum file and extracted ARM64 executable have independent pinned digests. Download/extraction never executes a core.

Startup probes only missing fresh URL-specific observations in reachable automatic groups and dialer dependencies, following the explicit member of manual groups. When validated rule caches are missing, it additionally probes non-DIRECT leaves of the default group at its configured URL and chooses an available resource node. It does not probe unrelated subscription nodes; the explicit measurement action may still test the retained groups. Automatic groups are probed using a short-lived unprivileged Xray observatory process with no inbound, TUN or API listener. Only exact pinned observer messages count as results; absent/malformed output is unavailable. Probe files remain private and are removed. All inherited `XRAY_*` and `xray.*` settings are cleared before running any owned core/probe, preventing injected config directories or inherited TUN descriptors.

Preparation cancellation sources are operation-owned, obsolete work cannot replace current progress, and historical failures are separate from current health. Refresh failures preserve the previous validated cache/runtime. Resource diagnostics identify stage/interface/port without exposing URL credentials.

## Privileged helper and restoration

The helper communicates only over a permission-restricted Unix domain socket. It authenticates UID, PID/start identity, executable path/hash and dynamic code identity against root-owned installation metadata. Frames are bounded, sessions/sequences echoed and checked; status observations must be fresh. The helper admits one native TUN, explicit physical interfaces and at most one TCP-only SOCKS resource listener on exact IPv4 loopback (port 1024–65535). It rejects wildcard listeners, UDP relay, caller-supplied HTTP/control APIs and direct resource routes. After validation, only the helper injects RoutingService on a Unix socket inside the root-owned 0700 private directory. No TCP control endpoint is opened. See [hot routing](mac-proxy-groups.md). Bootstrap is independently constrained to three exact routing stages ending in a deny rule; injected TUN tags cannot broaden its DNS exception.

Only the independently pinned official core may be installed/executed as root. User generation files are opened without following links, verified, copied into root-owned immutable generations, rechecked and tested before mutation. No user-writable executable is run as root. Installation stages verified helper/native bytes privately, replaces exact payloads and preserves rollback.

Original DNS dictionaries (including enabled/absent protocol state and unknown plist fields) are durably journaled before mutation. The helper confirms actual TUN address and pinned Xray IPv4/IPv6 route ownership before switching DNS. Stop, core/TUN failure, GUI loss and launchd restart attempt owned-core shutdown and DNS restoration independently. A failed process operation cannot skip DNS restoration; unresolved recovery retains the journal and unavailable status. No Internet/latency/telemetry result is used as a guardian verdict.

## Independent observations and usage

Guardian input contains authenticated main-instance liveness and actual TUN takeover only. Stale/read failures never produce healthy status. Production UI polls actual helper state; it does not create successful Internet/latency or traffic samples. The independent main-network state machine retains 30-second rounds, 5-second retries and three consecutive failures; no failed display request can restart TUN.

The usage ledger supports fixed 30-natural-day periods from first opening and a saved time zone, resume baselines, observed-outbound history and atomic checkpoints/totals. Production currently shows no traffic curve until a real observation source supplies samples; it never substitutes preview observations or estimates. No quota UI is present.

## Verification boundary

`python3 build/Verify-Mac.py` builds production GUI/helper code, runs only injected mock tests and pure native ABI/route-parser probes, renders isolated UI states and publishes both NativeAOT binaries. Packaged execution is restricted to explicit mock-smoke entrypoints. Computer Use UI checks must launch with `--preview`.

No automatic check installs launchd jobs, starts a real core/TUN, changes DNS/routes, terminates protected apps or reads the user's real configuration. Live TCP/UDP, DNS, IPv4/IPv6, helper authorization and interface-disconnect behavior remain user-run acceptance; they are not inferred from compilation or mocks.

## Connection activity

`XrayConnectionObserver` parses only the pinned core stdout/stderr grammar into bounded in-memory records. Optional snapshots piggyback on authenticated helper replies; malformed, stale, oversized or failing observation data cannot invalidate a valid lifecycle status or stop/restart the core. Telemetry uses no API/control listener and no per-connection disk log. RoutingService is a separate helper-private mutation channel, never a source of telemetry or guardian verdicts. Actual destination, transport, outbound and matched-rule tags may be displayed; unknown PID/path, bytes and active/closed states remain unknown. Access-history rows are never silently treated as active connections or fed into the usage ledger.

Desktop labels match the applied generation, never the editable draft. The running generation remains pinned through metadata-only publications; observed route classification and names stay stable across later edits. The virtualized UI supports search/app filters/sorting and a selected detail pane while preserving the inspected row and focus as new records arrive. Development screenshots and populated fixtures use explicit isolated previews only.


## Discovery, search and actionable startup failures

Application discovery accepts `.app` aliases at standard application roots, resolves metadata to the canonical bundle and deduplicates on that identity. The explicit system Cryptex Applications root covers current Safari installations. Linked shared directories are still excluded, nested helper bundles are not app rows, and discovery performs no Mach-O membership scans. Only explicit selection/refresh builds a fixed recursive inventory.

Application filtering includes name, bundle ID and saved paths; node filtering includes name/protocol/server/group without altering membership or routes. Local import and port settings use the shared presentation theme. Render checks cover normal/compact layouts, text input, empty results, Safari, local import, physical conflicts and retry states.

`RuntimeFailureException` carries only allow-listed codes and fixed user-facing text across helper IPC, coordinator results and the current-error surface. TUN name and SOCKS port conflicts are checked by the privileged runtime before starting the new owned core; interface availability and authorization failures retain distinct causes. A takeover deadline is an error, not user cancellation. Raw core output, credential-bearing exception text and routine connection errors are not forwarded into lifecycle status. Recovery failure is reported separately. An explicit Connect retry clears a stale applied-runtime assumption only after a fresh authenticated helper report confirms core/TUN loss; read failures cannot authorize replacement. UI/traffic observation still has no authority to restart TUN or determine guardian readiness.

### TUN lifecycle and physical link availability

TUN creation never tests physical link/IP availability. The UI retains disconnected service-to-BSD mappings, the production backend has no online-interface gate, and the helper validates configured service identity without using `IsActive` or addresses. Service identity still cannot be substituted; malformed/missing identities are configuration errors, distinct from an offline link. DNS backup failures have their own error code. The pinned [Xray Darwin socket implementation](https://github.com/XTLS/Xray-core/blob/v26.10.29/transport/internet/sockopt_darwin.go) applies interface binding when an outbound socket is opened; its binding errors fail that connection.

The connection attempt establishes TUN before required automatic-group observations. While observations are missing, transient bootstrap may route resources to `blocked` (never an arbitrary member or direct fallback); ordinary TUN traffic remains blocked. After valid observations, the same preparation transaction updates the resource route only if its generated configuration changed. Complete configurations cannot defer group selection. Cancel/failure restores the original pre-attempt generation across both bootstrap phases, and a ready unchanged resource route does not restart. Rule/probe failures appear after the TUN phase; authorization, port and TUN conflicts keep their specific startup errors. Guardian readiness remains independent of Internet/link health.
